# FODANVI scripts

Object detection on analog night vision captures: the captures, the
synthetic COCO conversions that imitate them, the detectors scored on both,
and the measurements behind the conversions.

Every command in this file runs from the repository root in PowerShell.
Results are not quoted here; they live in `data/results/` and the records
under `data/photometry/` and `data/day2night/`, and are regenerated by the
commands below.

## The order of things

| step | command | details |
| --- | --- | --- |
| 1. Place the downloads | by hand | [`data/README.md`](data/README.md) |
| 2. Prepare and annotate the captures | `ConvertRaw.py`, `GenerateCrops.py`, labelme, `.\ConvertAnnotations.ps1` | [Preparing the captures](#preparing-the-captures) |
| 3. Measure the device, build the conversion configs | `AnalyzeNVG.py` | [`data/day2night/README.md`](data/day2night/README.md) |
| 4. Build the converted COCO sets | `python BuildDay2NightDatasets.py` | [Converted COCO sets](#converted-coco-sets) |
| 5. Build the variants (tints, preprocessing) | `.\BuildDatasets.ps1` | [Dataset variants](#dataset-variants) |
| 6. Fine-tune (optional, the weights are downloaded) | `.\RunTrain.ps1` | [Fine-tuning](#fine-tuning) |
| 7. Score every model on every set | `.\RunSweep.ps1` | [Running every validation](#running-every-validation) |
| 8. Tables and figures | `CompareRuns.py`, the per-object tables | [Comparing the runs](#comparing-the-runs), [Per-object tables](#per-object-tables) |
| 9. Score variability | `BuildResampledSets.py`, `.\RunResampled.ps1` | [Resampled sets](#resampled-sets) |
| - Scene illuminance, device gain and grain | `SceneLux*.py` | [`data/photometry/README.md`](data/photometry/README.md) |

Steps 2, 3 and 6 are only needed to rebuild what is already versioned or
downloaded: the annotations are versioned and the captured datasets come
with the project data, ready to use, so step 2 needs the captures from the
same archive; the conversion configs are in `data/day2night/`, and the
fine-tuned weights are a download.
Reproducing the reported scores needs steps 1, 4, 5, 7 and 8.
Every converted set is built whole, train2017 and val2017; the sweep scores
val2017 only, so `--splits val2017` gets a sweep going before the training
splits are done.

Every wrapper script takes `-WhatIf`, which lists what it would do without
doing it.

## Data

Nothing under `data/` that is an image, a weight or a run is versioned, so
a fresh clone runs nothing until three downloads are in place:

- **the project data**, one download holding everything this project
  produced (the captured datasets, the fine-tuned weights, the photometry
  frames and the images) in the full `data/` structure, extracted into
  `data/` as it is;
- **COCO 2017**, the source of every converted set;
- **the pre-trained weights** of the five detectors.

The archive of the project data also holds **the captures**, the images as
the cameras wrote them, needed only to prepare the datasets again (step 2).
[`data/README.md`](data/README.md) has the links, where each goes, and what
under `data/` is downloaded, generated or versioned. Everything else is
built from these three by the steps below.

## Preparing the captures

The captures are frames of the eyepiece, a bright circular field in a black
surround. They are cropped to that field before annotation, and every set
derived from them carries the crop.

**Raw frames.** The Nikon D500 and phone captures are raw files, which the
detectors cannot read. `ConvertRaw.py` renders them to JPEG, by default with
the camera white balance and no automatic brightening, so a dark frame stays
dark; `--auto-bright` stretches it to the full range, which shows whether the
subject is there but is not what was captured. Report which one a figure
came from.

    python src\Processing\ConvertRaw.py <file|folder> [out_folder] [--auto-bright] [--quality 95]

**Cropping.** `GenerateCrops.py` finds the circular field in every image of a
folder, trims the outer tenth of its radius to drop the vignette, and writes
`<name>_cropped.jpg`. Files already carrying `_cropped` are skipped, so it can
be run on a folder holding both. Without an output folder it writes beside
the input.

    python src\Processing\GenerateCrops.py <in_folder> [out_folder]

**Annotation.** The real captures, the moving car frames and the phone
reference were annotated in labelme and converted to YOLO sets with
`.\ConvertAnnotations.ps1`. How to annotate, the conversion commands and
what the script checks are in
[`data/datasets/README.md`](data/datasets/README.md#annotation).

## Converted COCO sets

All converted COCO sets are built by one script in the repository root, with
COCO in place:

    python BuildDay2NightDatasets.py                       every set, both splits
    python BuildDay2NightDatasets.py --splits val2017      val first, train later
    python BuildDay2NightDatasets.py --only "coco_nvg2_*"  a subset by glob

| sets | generator | values | used for |
| --- | --- | --- | --- |
| `coco_nvg_{green,white}_{noisy,clean}` | `GenerateNVG.py` | hand-tuned, hardcoded in the script | v1 fine-tuning, validation |
| `coco_nvg2_green_{noisy,clean,grain}` | `GenerateNVGv2.py` | `data/day2night/nvg_config_selected_green.json` | v2 fine-tuning, validation |
| `coco_nvg2_white_{noisy,clean,grain}` | `GenerateNVGv2.py` | `data/day2night/nvg_config_selected_white.json` | v2 fine-tuning, validation |
| `coco_nvg_captures_green_{noisy,clean}` | `GenerateNVGv2.py` | `data/day2night/nvg_config_setup_green.json` (the evaluation captures) | validation |

The v2 fine-tuning trains on the references only, so that no statistic of the
evaluation captures reaches its training data; `coco_nvg2_clean.yaml` and
`coco_nvg2_noisy.yaml` pair green with white for its two stages. The captures
set is matched to the camera path the models are scored on and is not
trained on, but is built whole, both splits. The grain sets are built for
val2017 only: they exist to measure the denoising, and no model is trained
on them or on their variants.

The clean variant disables grain, blur, bloom and vignette. The grain-only
variant is the clean one with the grain left on, so it differs from the
clean set in the grain alone. The script only writes images and labels; every
yaml under `data/datasets` is versioned and already points at those folders.
A split is complete when it holds as many images and labels as COCO's; a
complete split is left alone, so an interrupted run resumes, and a split
whose images are all there but whose labels are not gets its labels copied
again without converting. `--force` rebuilds a split that is complete.

`GenerateNVG.py` is frozen and must not be edited. The v1 flags are as
recorded in `MA_Paper/supplementary/code/Readme.md`; the four-folder layout
is not, since the original calls wrote into a single `coco_nvg`. Rebuilding
the v1 sets gives complete sets, not necessarily the original ones: the green
noisy val2017 on disk came from an earlier revision of the script.

How the configs are measured, and the commands that write them, are in
[`data/day2night/README.md`](data/day2night/README.md).

### The yaml files combine them

Each config lists several folders under `train:` and `val:`, so a grouping
is a yaml rather than a copy of the images. Every set has a yaml of its own
under its folder name; the groupings beside them are:

| config | covers | used by |
| --- | --- | --- |
| `coco_nvg_clean.yaml` | v1 green clean + white clean | v1 first stage |
| `coco_nvg_noisy.yaml` | v1 green noisy + white noisy | v1 second stage |
| `coco_nvg_green.yaml` | v1 green clean + green noisy | kept for training |
| `coco_nvg_white.yaml` | v1 white clean + white noisy | kept for training |
| `coco_nvg2_clean.yaml` | v2 green clean + white clean | v2 first stage |
| `coco_nvg2_noisy.yaml` | v2 green noisy + white noisy | v2 second stage |

They set `path: /datasets`, which is the mount target inside the container,
not a host path. The `real_nvg` configs use `path: real_nvg...` with splits
relative to it, a different style that resolves the same way.

## Dataset variants

`sweep.json` drives this and the sweep below. Its `variants` block is a list
of source datasets and the generator chains to apply to each:

    "variants": [
      { "source": "real_nvg", "chains": [["grayscale"], ["white"], ["white", "dn_h80_w3"]] }
    ]

Every name in a chain comes from the `generators` block beside it, which
gives the script in `src/Processing`, the suffix that script appends, and
the extra arguments it takes after the input and output folders.

    .\BuildDatasets.ps1                        build whatever is missing
    .\BuildDatasets.ps1 -Only real_nvg_white   one of them, or a glob
    .\BuildDatasets.ps1 -Force                 rebuild even if present
    .\BuildDatasets.ps1 -WhatIf                list without building

A chain runs its generators in order, each over the previous one's output,
so `["grayscale", "white"]` gives `real_nvg_grayscale_white` with files
suffixed `_grayscale_white`. The dataset is named for its source and those
suffixes and is never named in the config, so the folder and the filenames
cannot disagree. Intermediate steps go to a staging folder that is deleted
on success, so a chain that dies half way cannot leave something that looks
like a finished dataset.

Labels are copied by `CopyFilesWithSuffix.py` with the same suffix, because
Ultralytics pairs an image with its label by stem. The script checks that
pairing and fails rather than write a dataset that would score zero without
explaining why.

The yaml it writes lands in `data/datasets/`. To be scored, the new set also
has to be named under `datasets` in `sweep.json`; see
[Running every validation](#running-every-validation).

### The generators

Two scripts do all the work:

- `GenerateColorShift.py` applies a per-channel formula over r, g and b,
  for the grayscale, white phosphor and red tints. The white tint ratios come
  from `data/day2night/nvg_config_selected_white.json`.
- `Preprocess.py` runs the steps of a json config in `data/preprocess/`:
  `equalize`, `clahe`, `denoise` (non-local means) and `resize`. The config
  holds only the transform; the file handling is on the command line. Its
  docstring documents every module and parameter.

The generator names encode their config: `dn_h80_w3` is denoise at h 80 with
a 3 pixel template window (search window 9), `cl_c0p75_t2` CLAHE at clip
0.75 on a 2x2 grid, `rs_640_lin` a resize to 640 on the longer side with
linear interpolation. `resave` runs no step and only re-encodes, as every
`Preprocess.py` output is, as a control for the JPEG encoding.

Either script runs on its own over a folder too:

    python src\Processing\Preprocess.py <in> <out> --config data\preprocess\dn_h80_w3.json --suffix _dn_h80_w3 --quality 95
    python src\Processing\GenerateColorShift.py <in> <out> --formula "g*0.561" "g" "g*0.874" --suffix _white

### Converted COCO sets as sources

An entry may name its `splits`; the default, `train` and `val`, is the layout
of the captures. A converted COCO set is laid out as `train2017` and
`val2017` and names both, so the variant is a whole dataset like its source.
A set built only to be scored names `["val2017"]` alone, and its yaml points
`train` at the val split, because the validator wants the key; the
denoised grain sets are built that way, as their sources are.

    { "source": "coco_nvg2_green_grain", "splits": ["val2017"], "chains": [["dn_h80_w3"]] }

    python BuildDay2NightDatasets.py --only "coco_nvg2_*_grain"
    .\BuildDatasets.ps1 -Only "coco_nvg2_*_grain_dn_h80_w3"
    .\RunSweep.ps1 -Datasets "coco_nvg2_*_grain*"

The denoised grain-only sets put the same denoising as the captures'
`dn_h80_w3` on the synthetic grain alone. The `coco_nvg2_*_noisy_dn_h80_w3`
sets, denoised from the full noisy conversion, still carry blur, bloom and
vignette and so do not compare with the clean set.

### Scale

The captures reach the model scaled down to 640 pixels, while the synthetic
sets already are 640 pixels, so a filter of fixed pixel size covers more of
the image on the synthetic sets. The `rs_640_lin` generators move the scaling
in front of the filter: `real_nvg*_rs_640_lin` is the captures resized as the
Ultralytics 8.4.41 loader resizes them (linear), and
`real_nvg*_rs_640_lin_dn_h80_w3` denoises after the resize. The Ultralytics
validators do not scale them again; RF-DETR still scales to its 560 pixels,
as for every other set. The resize is linear because area averaging would
smooth the grain on top, so the reference would no longer be the model's
input.

    .\BuildDatasets.ps1 -Only "real_nvg*rs_640_lin*"
    .\RunSweep.ps1 -Datasets "real_nvg*rs_640_lin*"

## Running every validation

    .\RunSweep.ps1

Every model in `sweep.json` against every dataset in it, one container per
pair, through the validator its `validators` entry names (`yolo_val.py`,
`rtdetr_val.py`, `rfdetr_val.py`).

    .\RunSweep.ps1 -WhatIf                list the runs without making them
    .\RunSweep.ps1 -Datasets real_nvg*    only the captures and their variants
    .\RunSweep.ps1 -Models yolo12x        one model
    .\RunSweep.ps1 -Force                 redo runs that already exist

Both halves of the matrix are named in `sweep.json`, under `models` and
`datasets`. Nothing is discovered, because `data/datasets/` also holds the
groupings kept for training, whose val splits are unions of the single sets
beside them. Sweeping the folder would score every converted image once
alone and once in each grouping it belongs to, and report them as separate
results.

Naming them has a cost: building a variant is not enough to get it scored,
it has to be added to `datasets` too. So the script lists any config in the
folder that it was not told about, rather than let a set that was built on
purpose go quietly unmeasured. A name in the list with no file behind it
stops the sweep before the first container.

Results land in `data/runs/val_<model>_<dataset>/`, named for the pair:

| in each run folder | what |
| --- | --- |
| `logs/console.log` | the whole run, progress redraws collapsed |
| `tables/per_class_metrics.csv` | one row per class, plus an `all` row |
| `tables/supercategory_metrics.csv` | the same averaged per COCO supercategory |
| `predictions.json` | every detection, so metrics can be recomputed |
| `confusion_matrix*.png`, `Box*_curve.png` | the usual Ultralytics plots |
| `val_batch*_{labels,pred}.jpg` | sample predictions against truth |

The two CSVs are the results. Nothing has to be read back out of the
terminal.

A run whose folder already exists is skipped, so an interrupted sweep
resumes by being started again. A missing weight or config fails before the
first container rather than an hour in. `data/runs/` is not versioned.

Budget hours, not minutes: every converted set is a 5000 image COCO
validation split, and RF-DETR installs itself into the container on every
run. `-Datasets real_nvg` alone checks the whole chain in minutes.

### Box annotations for RF-DETR

Nothing to run: `RunSweep.ps1` builds these itself when they are missing.
This is what it is doing when it prints `build box annotations for ...`.

The converted COCO sets carry segmentation polygons rather than boxes,
`cls x1 y1 x2 y2 ...`, because COCO ships masks and the conversion kept
them. Ultralytics derives the enclosing box itself, so YOLO and RT-DETR
score those sets normally. `rfdetr_val.py` has to be handed one, and it
refuses to build its own:

    python src\Processing\GenerateBoxAnnotations.py data\datasets\coco_nvg_green_clean.yaml

That writes `<config>_gt.json` beside the config. The sweep runs it on the
host, once per set, rather than letting the validator rebuild it in the
container on every run across the bind mount.

### A single run

For a pair the sweep does not cover, such as a model scored against
Ultralytics' own `coco.yaml` rather than anything in `data/datasets/`, the
validators run on their own. Each prints the per-class table and writes the
same run folder as the sweep; the last argument is the run name.

    docker run --gpus all --rm --shm-size=18g `
      -v ${PWD}\data\datasets:/datasets `
      -v ${PWD}\data\models:/models `
      -v ${PWD}\data\runs:/ultralytics/runs/detect `
      -v ${PWD}\src\Processing:/workspace `
      ultralytics/ultralytics:8.4.41 `
      python /workspace/yolo_val.py /models/yolo12x.pt coco.yaml val_yolo12x_coco80

    docker run --gpus all --rm --shm-size=18g `
      -v ${PWD}\data\datasets:/datasets `
      -v ${PWD}\data\models:/models `
      -v ${PWD}\data\runs:/ultralytics/runs/detect `
      -v ${PWD}\src\Processing:/workspace `
      ultralytics/ultralytics:8.4.41 `
      python /workspace/rtdetr_val.py /models/rtdetr-x.pt /datasets/real_nvg.yaml val_rtdetrx_real_nvg

    docker run --gpus all --rm --shm-size=18g `
      -v ${PWD}\data\datasets:/datasets `
      -v ${PWD}\data\models:/models `
      -v ${PWD}\data\runs:/ultralytics/runs/detect `
      -v ${PWD}\src\Processing:/workspace `
      ultralytics/ultralytics:8.4.41 `
      bash -c "pip install --quiet rfdetr==1.2.0 transformers==4.53.3 pycocotools && python /workspace/rfdetr_val.py /models/rf-detr-large.pth /datasets/real_nvg.yaml val_rfdetrl_real_nvg"

`GenerateResultTables.py` recomputes the per-class tables of a run from its
`predictions.json` and a COCO ground truth, without running inference again:

    python src\Processing\GenerateResultTables.py --pred <run>\predictions.json --gt <gt.json> --out <run>\tables

## Predicting on images with no labels

The sweep scores against ground truth. This is the other question: point a
model at a capture nothing has labelled and see whether the subject is
detected at all.

One script per model family, named for the validator beside it:

| family | script | notes |
| --- | --- | --- |
| YOLO | `yolo_predict.py` | |
| RT-DETR | `rtdetr_predict.py` | carries the same `scale_boxes` patch as its validator |
| RF-DETR | `rfdetr_predict.py` | needs the pip install |

The image folders under `data\images\` come with the project data; what
each holds is in [`data/README.md`](data/README.md#the-project-data).

### Every model at once

`RunSweep.ps1 -Predict` runs every model in `sweep.json` over a folder under
`data\images\`, one container and one run per model, through the predict
script beside each validator:

    .\RunSweep.ps1 -Predict vignetting
    .\RunSweep.ps1 -Predict predict -Models yolo12x    one model
    .\RunSweep.ps1 -Predict vignetting -Conf 0.05      lower threshold
    .\RunSweep.ps1 -Predict vignetting -WhatIf         list the runs

Runs are named `predict_<model>_<folder>`, so
`data\runs\predict_yolo12x_vignetting` is yolo12x on `data\images\vignetting\`.
Existing runs are skipped and `-Force` redoes them, as for validation. The
folder is read flat by the YOLO and RT-DETR scripts but recursively by
RF-DETR, so keep the images of one run in one folder without subfolders.

For the vignetting images, crop first, on the folder itself, so each
photograph sits beside its crop; `GenerateCrops.py` skips what is already
cropped:

    python src\Processing\GenerateCrops.py data\images\vignetting data\images\vignetting
    .\RunSweep.ps1 -Predict vignetting

### One model at a time

The same scripts in a container of their own. Each writes annotated images,
a per-image `.txt` of the detections and `logs/console.log` into
`data\runs\<name>\`; the arguments are weights, image folder, run name and
confidence threshold.

    docker run --gpus all --rm --shm-size=8g `
      -v ${PWD}\data\images\predict:/data `
      -v ${PWD}\data\models:/models `
      -v ${PWD}\data\runs:/ultralytics/runs/detect `
      -v ${PWD}\src\Processing:/workspace `
      ultralytics/ultralytics:8.4.41 `
      python /workspace/yolo_predict.py /models/yolo12x.pt /data predict_yolo12x 0.25

`rtdetr_predict.py` takes the same arguments; `rfdetr_predict.py` needs the
pip install of the RF-DETR validation command above in front of it.

0.25 is a reasonable threshold for looking at a picture, but the sweep
validates at 0.001 to maximise recall, so a subject can be found there and
invisible here. Before concluding a model sees nothing, try 0.05.

The classes are COCO's, so a subject that is not one of the 80 can only be
reported as whatever it most resembles, and an RC car has to come back as
`car` or `truck` or not at all.

## Comparing the runs

    python src\Processing\CompareRuns.py

Reads the `all` row of every run under `data\runs\` and writes into
`data\results\`:

    comparison.csv          one row per run
    matrix_map50_95.csv     dataset rows, model columns

plus every figure the `plots` block of `sweep.json` names (below), so this
one command redraws all of them after a sweep. Without a `plots` block it
draws one `bars_map50_95.png`, grouped bars with one group per dataset.

`--metric` switches all of them between `map50_95`, `map50`, `precision`
and `recall`. `--no-plots` writes the tables only.

What a run was is read from the run itself, from the `Model` and `Data`
lines the validators print into `logs/console.log`, so nothing has to be
told which folders to look at and a run stays readable after the config
that produced it has moved on. It prints how many runs it found, names any
with no tables yet, and warns when a weight's size is neither measurable
nor recorded.

Every run is scored on the classes in the `classes` list of `sweep.json`
(the four the real captures contain), as the mean of their rows in the run's
per-class table. A COCO run's `all` row averages all eighty, so without this
its baseline measures a different category mix than the real set. No
inference is repeated; `--all-classes` reports the `all` row instead.

The csv keeps every run, but the figures show only what `sweep.json` lists:
a run is drawn when its dataset is in the sweep's `datasets` and its weight
belongs to one of the sweep's `models`. This holds for the default figures
and for every `PlotRuns.py` selection below; `--all` draws every run.

Two size columns, not one. `file_mb` is what the checkpoint costs to fetch,
`weights_mb` the model parameters inside it. They differ where a file is a
training checkpoint; see [`data/models/README.md`](data/models/README.md).

### Two scoring paths

YOLO and RT-DETR are scored by Ultralytics, RF-DETR by pycocotools in
`rfdetr_val.py`. `CrossCheckScoring.py` rescores runs Ultralytics has
already scored through `rfdetr_val.py`'s own functions, from their saved
`predictions.json`, and writes both side by side:

    python src\Processing\CrossCheckScoring.py
    python src\Processing\CrossCheckScoring.py val_yolo12x_coco --sweep none `
        --out data\results\scoring_crosscheck_coco80.csv

The first compares the default runs (yolo12x on `coco` and `real_nvg`) over
the sweep's classes into `scoring_crosscheck.csv`; the second, given a sweep
file that does not exist, over all 80 classes. mAP agrees between the two
paths, so it can share a table. Precision and recall do not: Ultralytics
reads both at one confidence for all classes, where mean F1 peaks, and
`rfdetr_val.py` at each class's own F1 peak, which on a class with few
instances can be its few most confident hits.

### Drawing a subset

Everything at once is the record rather than the picture worth looking at,
so the figures worth keeping are named in the `plots` block of `sweep.json`,
each with a prefix, model and dataset globs and the metrics to draw:

    "plots": [
      { "prefix": "",         "models": "*",        "datasets": "*", "metrics": ["map50_95"] },
      { "prefix": "finetune", "models": "yolo11s*", "datasets": "*", "metrics": ["map50_95"] }
    ]

`CompareRuns.py` draws all of them, and so does `PlotRuns.py` on its own,
which redraws from the csv without collecting the runs again:

    python src\Processing\PlotRuns.py                                     every configured plot
    python src\Processing\PlotRuns.py --models "yolo11s*" --prefix test   one selection, not kept in the config

Adding a metric to `metrics` or a new entry to the block is how a figure
becomes part of the set. Each entry's `describe` says what it shows.

`models` and `datasets`, in the config or as `--models` and `--datasets`,
take comma separated globs matched against the csv, the prefix keeps a
selection from overwriting the default figures, and the metrics are the same
four as above. Models and datasets are drawn in the order of the globs that
pick them, so an entry that names them one by one sets the order.

An entry can also carry:

    "kind": "lines"        one line per model across the datasets, written as
                           <prefix>_lines_<metric>.png; the default is "bars",
                           <prefix>_bars_<metric>.png
    "kind": "panels"       grouped bars split into panels stacked on one
                           shared axis, <prefix>_panels_<metric>.png; takes
                           "styles" ("--" gives a hollow, hatched bar),
                           "width", "baseline", "columns" and "pairs" as
                           "lines" does
    "panels": [            panels only: each panel's title and datasets,
      {"title": "Green",   comma separated globs matched against the
       "datasets": "..."}  datasets drawn (or the labels of "columns" and
    ]                      "pairs"), in the order given; a dataset may stand
                           in several panels; without it, one panel
    "kind": "nested"       panels whose bars overlap, <prefix>_nested_<metric>.png:
    "slots": [             each slot one position per dataset, the first
      ["yolo11s"],         model a wide light bar, the second a narrow full
      ["a_clean",          one inside it; a slot of one model is a plain
       "a_clean-noisy"]    bar, a model in no slot is not drawn
    ]
    "kind": "heatmap"      one row per dataset, one column per model, each
                           cell colored and labeled with its figure,
                           <prefix>_heatmap_<metric>.png; "panels" groups the
                           rows with a rule between groups; a difference or change
                           gets a blue-red scale centered on zero; with more
                           models than datasets the grid turns, one row per
                           model, the rules then vertical
    "labels": {...}        model name to the text shown for it in the legend
                           (or heatmap column), in place of the run name
    "group": "model"       bars only: one group per model, one bar per dataset
    "colors": [...]        one color per model, in the order of "models"
    "styles": ["-", "--"]  lines and panels: one dash pattern per model, in the
                           same order; a dashed line gets hollow markers, in
                           panels a "--" model gets hollow, hatched bars
    "columns": [           not bars: each point is a label and dataset globs,
      {"label": "COCO", "datasets": "coco"},       and a model's point is its
      {"label": "green best preprocessing",        highest figure over the sets
       "datasets": "real_nvg_dn_*,real_nvg_cl_*"}  matched; which set that was
    ]                                              is printed
    "baseline": "yolo11s"  a model whose figure is subtracted from every other
                           model's on the same dataset, so the plot shows the
                           difference from it; it must be among the plot's models
                           and is not drawn itself
    "pairs": [             in place of "datasets": each point a model's
      {"label": "...",     figure on "dataset" minus its figure on "minus";
       "dataset": "...",   "change" names the axis
       "minus": "..."}
    ]

A label in `columns` must not contain a comma, since the order is passed on
as a comma separated list.

## Resampled sets

How far a score on a set as small as the captures moves when the images are
drawn differently is measured on resampled copies of the set:

    python src\Processing\BuildResampledSets.py --runs 100
    .\RunResampled.ps1
    python src\Processing\CompareRuns.py --runs data/runs_resampled --out data/results_resampled --no-plots

`BuildResampledSets.py` builds `--runs` sets of the same size as the source
(`--source`, default `real_nvg`). `--unique-pct` of each set (default 66.7)
is drawn without replacement, the rest are duplicates drawn from those; a
duplicate is copied under its own name with its label, so the validator
scores it as one more image. Set `r` is drawn with seed `--seed + r`, and
`manifest.json` lists the files of every set, so any set can be rebuilt.
`--reuse <source>` draws nothing but rebuilds the manifest's sets of that
source from `--source`, image for image, so a preprocessed variant holds the
same captures as each set of the captures as captured and two figures can be
compared set by set (the variant's files are matched by the source's file
name, which every preprocessing step keeps as the start of its own):

    python src\Processing\BuildResampledSets.py --source real_nvg_dn_h20_w5 --reuse real_nvg --runs 100
    .\RunResampled.ps1 -Sets "real_nvg_dn_h20_w5_rs_*"

The sets go to `data\datasets\resampled\`, each as
`<source>_rs_u<pct>_r<NNN>` with its own yaml, outside the dataset folder
proper so `RunSweep.ps1` neither sweeps nor reports them. `--out` has to stay
inside `data\datasets`, since the yaml names the container path. Existing
sets are skipped; `--force` rebuilds them.

`RunResampled.ps1` runs one model (`-Model`, default `yolo12x`, YOLO
validator only) against every set (`-Sets`, a glob) in a single container,
since starting one per set would cost more than the validation. Each set
still gets its own `yolo_val.py` process and run folder,
`val_<model>_<set>`, written to `data\runs_resampled\` rather than
`data\runs\`, so the resampled runs stay out of `comparison.csv` and the
sweep figures. Existing runs are skipped, so an interrupted batch resumes;
`-WhatIf` lists what would run. `CompareRuns.py` pointed at that folder
collects them, scored on the `classes` of `sweep.json` like every other run.

    python src\Processing\ResampledStats.py
    python src\Processing\ResampledStats.py --variant real_nvg_dn_h20_w5

`ResampledStats.py` summarizes the resampled runs of one model (`--model`,
default `yolo12x`) per category from each run's `per_class_metrics.csv`:
`data\results\resampled_variability.csv` for how far a single score on
`--source` moves (standard deviation, 1.96 of them, range, how many sets lie
within that band, and the standard deviation over the first 25, 50 and 75
sets), and with `--variant` `data\results\resampled_paired_<variant>.csv` for
how far the difference between the variant and the source moves when both are
scored on the same images, set by set.

## Fine-tuning

    .\RunTrain.ps1 -Stages nvg2_clean,nvg2_clean-noisy   the v2 chain
    .\RunTrain.ps1 -Stages nvg2_* -WhatIf                print the commands
    .\RunTrain.ps1 -Stages nvg2_clean -Set lr0=0.0002    override any train argument
    .\RunTrain.ps1 -Stages nvg2_clean -StopAfter 2       a short trial

`train.json` holds the device settings (image, GPU, shared memory, batch,
workers), the hyperparameters every stage shares and one entry per stage:
starting weights, training set, own arguments, `stop_after` and the file in
`data/models` its `best.pt` is exported to. Which stage produced which of
the four fine-tuned weights is in
[`data/models/README.md`](data/models/README.md#fine-tuned).

A stage keeps `epochs=100`, so it runs on the learning-rate schedule of a
100 epoch run, and is stopped once `results.csv` holds `stop_after` epochs.
A stage whose run folder exists is skipped; one interrupted resumes from its
`last.pt`; `-Force` redoes it and overwrites its export. Weights in
`data/models` that no run here produced, such as the downloaded fine-tuned
ones, are never overwritten without `-Force`. A stage trained further
invalidates the stages that started from its weights; rerun those with
`-Force`. The script's header documents the rest.

### The v1 stages by hand

The two v1 stages were run by hand before `RunTrain.ps1` existed, on
Ultralytics 8.3.221, the version both checkpoints record. `train.json` holds
them for the record. The commands:

    docker run --gpus all --rm --shm-size=12g `
      -v ${PWD}\data\datasets:/datasets `
      -v ${PWD}\data\models:/models `
      -v ${PWD}\data\runs:/ultralytics/runs/detect `
      ultralytics/ultralytics:8.3.221 `
      yolo detect train model=/models/yolo11s.pt data=/datasets/coco_nvg_clean.yaml `
        optimizer=SGD lr0=0.0001 lrf=0.01 momentum=0.937 warmup_epochs=5.0 `
        epochs=100 batch=16 imgsz=640 patience=30 workers=4 `
        project=/ultralytics/runs/detect name=finetune_yolo11s_nvg_clean

    docker run --gpus all --rm --shm-size=12g `
      -v ${PWD}\data\datasets:/datasets `
      -v ${PWD}\data\models:/models `
      -v ${PWD}\data\runs:/ultralytics/runs/detect `
      ultralytics/ultralytics:8.3.221 `
      yolo detect train model=/models/yolo11s_clean.pt data=/datasets/coco_nvg_noisy.yaml `
        optimizer=SGD lr0=0.0005 lrf=0.01 momentum=0.937 warmup_epochs=5.0 `
        epochs=100 batch=16 imgsz=640 patience=30 workers=4 `
        project=/ultralytics/runs/detect name=finetune_yolo11s_nvg_clean-noisy

Ultralytics writes the checkpoint to `data/runs/<name>/weights/best.pt`; copy
it into `data/models/` under the name the sweep expects.

Notes on these settings:

- `optimizer=SGD` has to be set. The default `optimizer=auto` ignores `lr0`
  and `momentum` and picks its own, which logs
  `optimizer: 'optimizer=auto' found, ignoring 'lr0=0.0001' and 'momentum=0.937'`
  and trains at `SGD(lr=0.01, momentum=0.9)`, far too high for this domain
  shift.
- A first run at `lr0=0.0001` and `epochs=50` diverged within four epochs.
  Doubling the epochs to 100, which stretches the schedule, and 5 warmup
  epochs let it recover from a similar early drop and keep improving.
- The first attempts failed during validation in epoch 1 from running out of
  resources. `workers=4` needs WSL to be given enough of them, in
  `notepad "$env:USERPROFILE\.wslconfig"`, taking effect after
  `wsl --shutdown`:

      [wsl2]
      memory=28GB
      swap=8GB
      processors=12

- Keep the machine from sleeping during long runs:

      powercfg /change standby-timeout-ac 0
      powercfg /change monitor-timeout-ac 0
